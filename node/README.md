# שירות סנכרון Surense → Postgres → API

שירות Node.js שמושך לידים מ-Surense CRM, שומר כל שינוי ב-Postgres, וחושף API מאובטח שממנו אפשר למשוך את השינויים ולשלוח הודעות.

**ה-CRM נקרא בלבד.** שלוש קריאות בסנכרון הרגיל: `POST /oauth/token`, `GET /leads/fields`, `POST /leads/search`. חיפוש קטלוג המקורות (`POST /api/sources/probe`) מוסיף עוד כמה `GET` — וגם הן קריאה בלבד. אין `PATCH`, אין `PUT`, אין `DELETE` בשום מקום בקוד.

---

## שני מסלולים, ושניהם נחוצים

המסמך המקורי קבע ש"אין Webhooks ב-Surense". **זה לא נכון** — ל-Surense יש webhooks מלאים דרך Svix.

| מסלול | מה הוא נותן | מה חסר בו |
|---|---|---|
| **Webhook** | שינוי סטטוס **מיידי**, עם `before`/`after` מוכנים | אין בו את המקור המפנה |
| **Polling** | כל שדות הליד, כולל המקור | רץ כל שעה, לא מיידי |

הם משלימים זה את זה: ה-polling מחזיק את נתוני הליד שלמים, וה-webhook הופך את שינוי הסטטוס למיידי. כשדחיפה מגיעה, השירות מוצא את הליד לפי `leadId` ולוקח ממנו את המקור.

### מה Surense שולחת

```json
{
  "eventType": "LeadUpdated",
  "leadId": "f7651ffc-...",
  "leadNumber": 3500,
  "customerName": "רועי סלאח",
  "date": "2026-09-04T13:25:41Z",
  "diff": {
    "statusName": { "before": "חדש", "after": "לא ענה" },
    "statusId":   { "before": "23545862-...", "after": "d2990176-..." },
    "closed":     { "before": true, "after": false }
  }
}
```

השינוי מגיע **מוכן** — אין מה להשוות. חותמת הזמן נלקחת מ-`date` שבאירוע ולא מרגע הקליטה, כך שדחיפה מושהית או שנשלחה מחדש נרשמת בזמן הנכון.

### הגנות בקליטה

**חתימה מאומתת** — Svix חותם את הגוף; דחיפה בלי חתימה תקפה נדחית ב-401.

**מניעת כפילות** — Svix מנסה שוב אחרי כישלון **עם אותו Message ID**. השירות שומר את המזהה ודוחה חזרה שנייה, אחרת אותו שינוי סטטוס היה מייצר שתי הודעות למקור.

**תשובה 200 גם כשלא נרשם כלום** — אירוע שאינו עדכון ליד, או ליד שהסנכרון עוד לא ראה, נשמר ומדווח אבל לא נכשל. 4xx היה גורם ל-Surense לנסות שוב ושוב משהו שלעולם לא יצליח.

`GET /api/webhooks` מציג את כל הדחיפות עם מה יצא מכל אחת. `?pending=true` מציג רק כאלה שנתקעו.

## הנתונים

**המסד מתחיל ריק ומתמלא לאט.** אין בו עותק של ה-CRM, וזו החלטה ולא חוסר: ה-CRM הוא מקור האמת ללידים, והעתקה של 3,283 שורות כל שעה כדי לענות על שאלה לגבי התריסר שזזו הייתה עבודה שאף אחד לא צריך.

| טבלה | מה יש בה |
|---|---|
| `status_events` | **הרשומה. שורה לכל שינוי סטטוס** — הלקוח, מאיזה סטטוס לאיזה, המטפל, והמקור המפנה |
| `sources` | מזהה מקור ← שם. נטען מה-CRM בקריאה אחת |
| `templates` | סטטוס ← נוסח ההודעה |
| `recipients` | מקור מפנה ← מייל/וואטספ |
| `webhook_events` | הדחיפות כמו שהתקבלו, לפני כל פרשנות |
| `leads`, `changes` | המראה הישנה. **ריקה כברירת מחדל** — `MIRROR_LEADS=true` מחזירה אותה |

### ההיסטוריה לא נמחקת. גם לא בטעות.

`status_events` היא append-only, **ומסד הנתונים אוכף את זה** — לא הקוד:

```sql
DELETE FROM status_events;    -- ERROR: status_events is append-only
TRUNCATE status_events;       -- ERROR: status_events is append-only
```

הנקודה היא ששינוי עתידי בקוד **לא יכול** למחוק את הרשומה בשקט. יש דלת יציאה, והיא רועשת בכוונה — צריך להצהיר על זה באותה טרנזקציה:

```sql
BEGIN; SET LOCAL app.allow_history_delete = 'on'; DELETE FROM status_events; COMMIT;
```

`POST /api/admin/reset-mirror?confirm=delete-mirror` מרוקן את המראה הישנה (`leads`, `changes`, ריצות, דחיפות) ו**לא נוגע בהיסטוריה**. זו הפעולה החד-פעמית שמתחילה מנקי.

## מה קורה כששינוי סטטוס מגיע

```
Surense ──webhook──► נרשם מיד ──► נקרא חזרה מה-CRM ──► נשמר ──► מוצג באתר
                     (לא תלוי                (2 קריאות)
                      בכלום)
```

**1. נרשם מיד.** השורה נכתבת לפני כל קריאה ל-CRM: שם הלקוח, מספר הליד, מאיזה סטטוס לאיזה, ומתי — לפי הזמן שבאירוע, לא לפי רגע הקליטה.

זה הסדר, והוא כל התכנון: זיהוי המקור דורש את ה-CRM, ו-CRM איטי או מושבת חייב לעלות לנו *העשרה שאפשר לנסות שוב* — לא את האירוע עצמו, שמגיע פעם אחת.

**2. נקרא חזרה.** שתי קריאות, ורק בפעם הראשונה:

| קריאה | מה מחזירה |
|---|---|
| `POST /leads/search` עם פילטר על ה-id | `sourceId` ו-`assigneeName` של הליד |
| `GET /customers/sources` | כל המקורות, מזהה ושם — **בקריאה אחת** |

הקטלוג נשמר ב-`sources`, אז מקור עולה בקשה אחת בפעם הראשונה שמישהו מפנה דרכו, ואפס אחר כך. באצווה של מאה אירועים שמזכירים מקור חדש — רענון אחד, לא מאה.

> **השם יושב תחת `title`, לא `name`.** חיפוש של `name` מחזיר שורה בלי שם בכלל, והמיפוי נשאר ריק בשקט. זו הייתה המלכודת, והיא מכוסה בבדיקה.

**3. נשמר ומוצג.** אם הקריאה נכשלה השורה נשארת `pending`/`failed` עם הסיבה, ו-`POST /api/events/enrich` מנקה את התור אחר כך. האירוע עצמו כבר בטוח.

`source_state` אומר איפה זה עומד: `pending` (עוד לא נבדק), `resolved` (יש שם), `absent` (ל-CRM אין מקור לליד הזה — תשובה, לא כישלון), `failed` (נוסה ולא הצליח; יש סיבה בשורה).

## ה-API

כל הנתיבים דורשים `Authorization: Bearer <API_TOKEN>` חוץ מ-`/health`.

### קריאת שינויים — התהליך שאתה רוצה

```bash
# 1. איפה הפסקתי?
curl -H "Authorization: Bearer $TOKEN" $URL/api/cursor/notifier
# → { "name": "notifier", "lastId": 412, "latestChangeId": 480 }

# 2. מה חדש מאז?
curl -H "Authorization: Bearer $TOKEN" "$URL/api/changes?sinceId=412&limit=100"
# → { "count": 68, "nextCursor": 480, "changes": [ ... ] }

# 3. אחרי ששלחת את ההודעות — שמור את המקום
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"lastId": 480}' $URL/api/cursor/notifier
```

**ה-cursor זז רק קדימה.** בקשה מאוחרת שנושאת מיקום ישן לא תחזיר אותו אחורה ולא תגרום לשליחה כפולה.

### חלופה: סימון ברמת השינוי הבודד

```bash
curl -H "Authorization: Bearer $TOKEN" "$URL/api/changes?pending=true"
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"ids":[471,472,473],"via":"whatsapp"}' $URL/api/changes/notified
# → { "requested": 3, "claimed": 3, "alreadyClaimed": [] }
```

`claimed` מחזיר רק את מה ש**באמת** תפסת. שני תהליכים שרצים במקביל יקבלו קבוצות זרות — אף הודעה לא תישלח פעמיים.

## הפער: ללידים אין שם מקור, רק מזהה

זו הבעיה שחסמה את כל שכבת ההודעות, והיא שווה הסבר כי היא לא נראית כמו תקלה.

הליד נושא `sourceId` — UUID, ותו לא. טבלת הנמענים מפתחה הוא **השם** של המקור, כי שם זה מה שיש בקובץ שלך. בלי גשר בין השניים כל ליד נדחה עם `lead-has-no-source`, ה-outbox מחזיר רשימה ריקה, והמערכת **נראית תקינה לגמרי** — היא פשוט לא שולחת כלום. `distinctSources: 0` על 3,279 לידים היה הסימן היחיד.

**כל ישות אחרת ב-CRM מגיעה כזוג:** `statusId`/`statusName`, `interestId`/`interestName`, `ownerId`/`ownerName`, `leadTypeId`/`leadTypeName`. המקור הוא היחיד מבין 78 השדות שמגיע בלי שם. גם הדחיפות של Svix נושאות `leadTypeName` — ואת המקור לא.

**השם לא ניתן לשחזור מהליד.** נבדק, לא נוחש: אף שדה מבין ה-78 אינו נקבע פונקציונלית על ידי `sourceId` חוץ מקבועים גלובליים (`tenantId`, `agencyId`). כלומר אין ב-161 המקורות שבשימוש שום עמודה נסתרת שמחזיקה את השם. הוא חייב להגיע מבחוץ.

### שלוש דרכים לגשר, לפי סדר עדיפות

**1. הקובץ שלך, עם עמודת מזהה.** הדרך הקצרה ביותר. הוסף לגיליון הנמענים עמודה `מזהה מקור` (או `sourceId` / `מזהה` / `קוד מקור`), והיבוא הרגיל ימלא גם את הכתובות וגם את המיפוי בפעולה אחת:

```csv
מקור,מזהה מקור,מייל
מטאור - אריאל יואב דביר,ce934d66-7cf3-4b94-84cf-929ba7953d9f,ariel@example.com
```

התצוגה המקדימה מדווחת `sourceIdsInFile` ו-`sourceIdsMapped`, כך ש-0 בשדה הראשון אומר מיד שהעמודה לא זוהתה.

**2. לחפש את הקטלוג ב-CRM.**

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" $URL/api/sources/probe
```

איזה נתיב מגיש רשימת מקורות אינו מתועד, ולכן הוא לא מנוחש: הבדיקה מנסה את סכמת השדות (שכבר נקראת בכל סנכרון — אם `sourceId` הוא שדה בחירה, המיפוי כבר מגיע ופשוט נזרק) ואת נתיבי ה-`GET` המועמדים, ואז **מדרגת כל מועמד מול התעבורה האמיתית**:

```json
{ "leadSourceIds": 161,
  "candidates": [
    { "path": "GET /leads/sources", "ok": true,
      "matchedSources": 158, "matchedLeads": 3244, "coverage": 0.9893 },
    { "path": "GET /sources", "ok": false, "status": 404 }
  ] }
```

קטלוג שמסביר 3 מקורות מתוך 161 הוא הקטלוג הלא נכון, כמה שהמבנה שלו יתאים; אחד שמסביר 158 הוא הנכון גם אם נמצא בנתיב לא צפוי. **זו הסיבה שהדירוג קיים** — בלעדיו הייתה כאן הימור שנכשל בשקט. `?apply=true` שומר את המנצח, ורק אם הוא באמת פתר משהו: טבלה מלאה בשמות סבירים-אך-שגויים גרועה מטבלה ריקה, כי ריקה מדלגת ושגויה שולחת מייל לשותף הלא נכון.

אם שום מועמד לא מסביר כלום, זה נאמר במפורש — וזו התשובה שצריך לקחת ל-Surense: *"איזה נתיב מגיש את רשימת המקורות?"*

**3. ביד.** תמיד עובד, ולא נדרס:

```bash
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '[{"sourceId":"ce934d66-...","name":"מטאור - אריאל יואב דביר"}]' \
  $URL/api/sources/map
```

מיפוי שנכתב ביד מסומן `manual` ו**סנכרון לא מוחק אותו**. שם שתוקן ידנית והוחזר לקדמותו כל שעה על ידי הסנכרון הוא בדיוק סוג התקלה שלא מבחינים בה.

### מאיפה מתחילים

```bash
curl -H "Authorization: Bearer $TOKEN" $URL/api/sources
```

`unresolved` מחזיר את המזהים שאין להם שם, **מהעמוס לדל**. ארבעת הראשונים מכסים 1,451 מ-3,279 הלידים — 44% מהתעבורה בארבע שורות. זה סדר העבודה.

`GET /api/diagnostics` מחזיק את אותם מספרים תחת `sourceMappings` ו-`unresolvedLeads`, כך שגשר ריק בולט בלי לחפש אותו.

### מה קורה עד שהגשר קיים

ליד שיש לו מזהה בלי מיפוי נדחה כ-`source-id-not-mapped`, ולא כ-`lead-has-no-source`. ההפרדה מכוונת: הראשון אומר "ה-CRM אמר לנו משהו שאיננו יודעים לקרוא", השני אומר "ה-CRM לא ייחס את הליד לאף אחד". התיקון שלהם הפוך, ואיחוד שלהם היה מסתיר איזה מהם באמת קורה.

## שכבת ההודעות — מה נשלח ולמי

השרת לא שולח כלום. הוא **מחליט** ומגיש החלטה מוכנה; הקוד המתוזמן שלך שולח. זה מה שמאפשר לבדוק את כל ההיגיון בלי שרת דואר, ומה שהופך הרצה יבשה לאותו מסלול קוד בדיוק.

### שתי טבלאות שאתה שולט בהן דרך ה-API

**`templates`** — סטטוס ← נוסח. שמונת הסטטוסים שהמסמך שלך נותן להם נוסח נזרעים אוטומטית בהפעלה הראשונה. **סטטוס בלי שורה כאן לא שולח כלום** — הרשימה סגורה, וזה מה שמשאיר את 34 הסטטוסים שטרם הוגדרו שקטים במקום לנחש.

```bash
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '[{"status":"נסגר","message":"הטיפול בליד הסתיים"}]' $URL/api/templates
```

הזריעה רצה **רק על טבלה ריקה**. אחרי שתערוך נוסח, deploy הבא לא יחזיר את המקורי.

**`recipients`** — מקור מפנה ← מייל. המפתח נגזר מנרמול השם, לא מתקבל מהקורא, כדי שיתאים בדיוק לאיך ששם מקור מנורמל בזמן השליחה.

```bash
curl -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '[{"sourceName":"מטאור - אריאל יואב דביר","email":"ariel@example.com"}]' \
  $URL/api/recipients
```

### יבוא קובץ הנמענים

יש לך כבר קובץ עם המיילים. שמור אותו כ-CSV מאקסל (File → Save As → CSV UTF-8) ו:

```bash
# 1. תצוגה מקדימה — לא כותב כלום
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: text/csv" \
  --data-binary @recipients.csv $URL/api/recipients/import

# 2. אחרי שבדקת את הדוח
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: text/csv" \
  --data-binary @recipients.csv "$URL/api/recipients/import?apply=true"
```

**קרא את התצוגה המקדימה לפני שאתה מאשר.** זה מה שהיא מחזירה:

```json
{
  "applied": false,
  "parsed": 47,
  "matchedSources": 41,
  "matchedLeads": 1832,
  "unmatchedFileRows": ["סוכנות ישנה - דוד", "מטאור-צפון"],
  "sourcesWithoutAddress": [
    { "source": "קמפיין", "leads": 485 },
    { "source": "חבר מביא חבר", "leads": 291 }
  ],
  "rejected": [{ "line": 12, "reason": "malformed-email", "detail": "ariel at example.com" }],
  "columnsDetected": { "sourceName": 0, "email": 1, "whatsapp": 2, "active": null }
}
```

| שדה | למה זה חשוב |
|---|---|
| `matchedLeads` | כמה לידים מכוסים בפועל — לא כמה שורות בקובץ |
| `unmatchedFileRows` | שורות שלא תואמות **שום** מקור בלידים. אלה שקטות לנצח — שם שהשתנה או טעות הקלדה |
| `sourcesWithoutAddress` | מקורות עם לידים שאין להם כתובת, מהעמוס לדל |
| `columnsDetected` | איזו עמודה נקראה כמה. ניחוש שגוי כאן בולט מיד |

**כותרות מזוהות אוטומטית**, בעברית ובאנגלית, בכל סדר: `מקור`/`source`, `מייל`/`דוא"ל`/`email`, `וואטספ`/`טלפון`, `פעיל`/`active`. יבוא חוזר **מעדכן** ולא מכפיל.

### מאיפה מתחילים למלא

```bash
curl -H "Authorization: Bearer $TOKEN" $URL/api/sources
```

מחזיר כל מקור שהלידים באמת משתמשים בו, **מהעמוס לדל**, עם דגל אם כבר יש לו כתובת. זה הופך את מילוי הטבלה מניחוש לרשימת עבודה.

### המזהה מול השם — למה צריך `source_names`

לליד ב-Surense **אין שם מקור**. מתוך 79 השדות שהוא מחזיר, מה שיש הוא `sourceId` — UUID. קובץ הנמענים לעומת זאת בנוי לפי **שמות** של שותפים. בלי גשר בין השניים אף הודעה לא תישלח אף פעם: המקור של כל ליד הוא UUID שלא תואם לשום שורה ב-`recipients`.

`source_names` הוא הגשר. אתה ממלא אותו מבחוץ — למשל בפנייה ל-CRM לכל `sourceId` — והתוצאה נשמרת, כך שהפנייה עולה **קריאה אחת למקור** ולא קריאה לכל ליד. בפועל: ~160 מזהים מול 3,279 לידים.

```bash
# מה עוד חסר, מהעמוס לדל
curl -H "Authorization: Bearer $TOKEN" $URL/api/source-names

# מילוי
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '[{"sourceId":"2f3a9c1e-...","sourceName":"מטאור - אריאל יואב דביר"}]' \
  $URL/api/source-names
```

מזהה שאין לו שם **לא נשלח** ומדווח כ-`source-id-not-mapped` — סיבה נפרדת מ-`source-not-in-recipients`. לשתיהן תיקון אחר: אחת דורשת שורה ב-`source_names`, השנייה שורה בקובץ הנמענים, וערבוב ביניהן שולח את מי שממלא אותן לטבלה הלא נכונה.

אם ב-CRM אחר העמודה כבר מכילה שם ולא מזהה — לא צריך למלא כלום. המיפוי נכנס לפעולה רק כשהערך נראה כמו UUID.

### ה-outbox — מה שהקוד המתוזמן קורא

```bash
curl -H "Authorization: Bearer $TOKEN" $URL/api/outbox
```

```json
{
  "pendingChanges": 47,
  "readyToSend": 3,
  "floodBrake": null,
  "skipped": {
    "no-template":            { "count": 31, "examples": [] },
    "source-not-in-recipients": { "count": 13, "examples": ["קמפיין", "חבר מביא חבר"] }
  },
  "messages": [
    {
      "changeId": 812,
      "to": "ariel@example.com",
      "subject": "עדכון סטטוס ליד — דנה כהן",
      "body": "שלום אריאל,\n\nעדכון בליד שהפנית:\n\nלקוח: דנה כהן\n...",
      "status": "לא עונה 3",
      "statusBefore": "לא עונה 2"
    }
  ]
}
```

ההודעה כבר מורכבת. הקוד שלך שולח אותה, ואז:

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"ids":[812],"via":"email"}' $URL/api/events/notified
```

`skipped` מקובץ לפי סיבה ולא שורה-לכל-דילוג — 31 סטטוסים בלי נוסח זו שורה אחת, לא 31.

### בלם ההצפה

יותר מ-`MAX_SENDS_PER_RUN` הודעות בריצה אחת, וה-outbox מחזיר **`messages: []`** ומסביר למה:

```json
{ "readyToSend": 0,
  "floodBrake": { "blocked": 212, "limit": 25, "statuses": ["לא עונה זמן רב"] } }
```

עדכון סטטוס המוני ב-CRM היה משגר 212 הודעות ללקוחות אמיתיים תוך דקה, ואי אפשר לבטל אף אחת. אחרי שבדקת ואתה רוצה לשחרר בכל זאת:

```bash
curl -H "Authorization: Bearer $TOKEN" "$URL/api/outbox?maxPerRun=300"
```

### מצב פיילוט — רשת ביטחון

```
REDIRECT_ALL_TO=shai@example.com
```

כל עוד יש כאן כתובת, **כל הודעה מנותבת אליה** במקום למקור המפנה. לידים אמיתיים, סטטוסים אמיתיים, נוסח אמיתי — ואף אחד בחוץ לא יכול לקבל הודעה בטעות.

- הנושא מקבל תווית `[פיילוט → ariel@example.com]` כדי שאי אפשר יהיה לבלבל בין הודעת פיילוט לאמיתית
- **הגוף נשאר בדיוק כמו שייצא באמת**, אז אתה בודק את הנוסח האמיתי
- `GET /api/outbox` מחזיר `redirectAllTo` בכל תשובה, כך שהפניה שנשארה דלוקה בטעות בולטת מיד — וכזו שכבויה לפני עלייה לאוויר בולטת גם

**מחיקת המשתנה הזה היא הפעולה המכוונת שמעלה את המערכת לאוויר.**

### הרצה יבשה

`GET /api/outbox` **הוא** ההרצה היבשה — הוא לא שולח, רק מראה. תריץ אותו, תסתכל על `messages`, ורק כשהנוסח נראה נכון תחבר את השליחה.

## מה נשלח, ובאילו סטטוסים

`src/notify/seeds.js` מחזיק את כל המדיניות: **23 סטטוסים ששולחים**, ו-**22 שמושתקים במפורש**.

השתקה היא ברירת המחדל בלי קשר — סטטוס בלי נוסח לא שולח כלום — אז הרשימה המושתקת לא משנה התנהגות. היא קיימת כי "החלטנו לא לשלוח" ו"אף אחד עוד לא כתב את זה" נראים זהים בטבלה ריקה, ורק אחד מהם בטוח לתקן על ידי הוספת נוסח.

**כל 42 הסטטוסים שה-CRM באמת מחזיק מסווגים** — 22 שולחים (2,250 לידים), 20 מושתקים (1,029). יש בדיקה שנכשלת אם סטטוס נופל בין הכיסאות.

### הזוגות שנבדלים במילה אחת

זה מה שהיה נשלח לשותף הלא נכון:

| מושתק | שולח |
|---|---|
| `חתימה` | `בחתימה` |
| `לאחר בדיקה` | `לאחר בדיקה לא זכאי` |
| `הוגש - ממתין למסמכים מהלקוח` | `הוגש` |
| `טיפול הסתיים - שולם סוכן` | `טיפול הסתיים - שולם לקוח` |

ההתאמה מדויקת, לא לפי תחילית.

### מקף ומרכאות — שתי מלכודות אמיתיות

ה-CRM שומר `טיפול הסתיים - שולם סוכן` עם **מקף רגיל**, והמפרט נכתב עם מקף ארוך (`–`). נוסח שנכתב עם מקף ארוך **לעולם לא היה מתאים**, וההודעה פשוט לא הייתה יוצאת. אותו דבר עם `י''כ שנפלו` (שני גרשים) מול `י"כ`.

הנרמול מטפל בשניהם, והבדיקות מוודאות גם שהם מתאימים **וגם** שהזוגות שלמעלה נשארים נפרדים.

### `{total}` — הסכום

שני נוסחים מצטטים סכום: `הוגש` ו-`טיפול הסתיים - שולם לקוח`.

**אין שדה כזה ב-78 שה-CRM מחזיר.** בדקתי. לכן `TOTAL_COLUMN` ריק, ושתי ההודעות האלה **נעצרות** במקום לצאת עם `{total}` בתוכן. ברגע שתגיד לי מה שם השדה — משתנה אחד וזה זורם.

הכלל כללי: הודעה שנשאר בה placeholder שאיש לא הגדיר (טעות הקלדה בנוסח) נעצרת ומדווחת. שדה ריק לגיטימי — מטפל שלא מוגדר — לא עוצר כלום.

## הדשבורד

```
https://your-app.onrender.com/dashboard
```

קישור רגיל בדפדפן. השירות מגיש אותו בעצמו, בלי אתר נפרד ובלי תלות חיצונית אחת.

| עמודה | |
|---|---|
| מתי | לפי זמן האירוע, בשעון ישראל |
| שם הלקוח, מספר ליד | |
| מסטטוס ← לסטטוס | |
| מטפל | `assigneeName` מה-CRM |
| מקור מפנה | השם שנפתר מה-`sourceId` |
| **טופל** | האם יצאה הודעה |

**ארבעה מצבים ל"טופל", ולא שניים:**

| מצב | מה זה אומר |
|---|---|
| **נשלח** | יצאה הודעה — עם מתי ולאן |
| **ממתין לשליחה** | הריצה הבאה תשלח |
| **ממתין לזיהוי המקור** | האירוע נרשם, המקור עוד לא נבדק מול ה-CRM |
| **לא יישלח** | **שום דבר לא ישלח** עד שיתוקן משהו — ומופיעה הסיבה |

"עוד לא נשלח" אחד לכולם היה מסתיר פער קבוע מאחורי מילה שמבטיחה שהוא זמני. ליד שתקוע על "אין נוסח לסטטוס הזה" לא ממתין לכלום.

**המצב לא מחושב מחדש בדף** — האירועים עוברים דרך אותו `buildEventOutbox` שמחליט מה באמת נשלח, והדף מתרגם את התשובה. אחרת מסך ומערכת היו נפרדים בשקט, ודווקא למסך מאמינים.

**מיון לפי תאריך** — לחיצה על כותרת "מתי" הופכת את הסדר, והחץ מראה את הכיוון הנוכחי. **עמודת ערוץ** אומרת במה ההודעה יצאה, ו"כל הערוצים" מסנן לוואטסאפ או למייל בלבד — ככה רואים מיד מה נשלח בוואטסאפ ומה עוד לא.

חיפוש (לקוח / מספר ליד / מקור / מטפל), סינון לפי טופל־לא טופל, סטטוס ומטפל, לחיצה על שורה פותחת את הפרטים כולל מצב זיהוי המקור והשגיאה אם הייתה. הסינון רץ ב-SQL, אחרת "לא טופל" היה מחזיר עמודים חלקיים וסך הכול שגוי.

**אבטחה:** הדף עצמו לא מחזיק שום נתון ולכן מוגש בלי טוקן — אין בו מה לדלוף. הוא מבקש את ה-`API_TOKEN` בכניסה ושומר אותו ב-`sessionStorage` של הלשונית בלבד. הטוקן לא עובר ב-URL בכוונה: כתובת עם טוקן נשמרת בהיסטוריה, ביומני proxy ובכותרת referer.

`render.yaml` בתיקייה. Render → New → Blueprint → בחר את ה-repo.

**עלות אמיתית: $6 לחודש.**

| רכיב | תוכנית | למה |
|---|---|---|
| Web service | **חינם** | 750 שעות בחודש. נרדם אחרי 15 דק' — ראה למטה |
| Postgres | **basic-256mb, $6** | ה[חינמי נמחק אחרי 30 יום](https://render.com/changelog/free-postgresql-instances-now-expire-after-30-days-previously-90) |

**SQLite לא אופציה כאן.** [הדיסק בשירות החינמי נמחק](https://render.com/docs/free) בכל deploy, restart או הירדמות — הקובץ פשוט ייעלם ואיתו כל ההיסטוריה.

### הסנכרון רץ ברקע

קריאה מלאה של כמה אלפי לידים לוקחת כדקה — 66 קריאות עוקבות ל-Surense. בקשת HTTP שנמשכת כל כך הרבה **נכשלת בכל מקום שחשוב**: לקוח שורת פקודה מוותר, הפלטפורמה סוגרת את החיבור, מתזמן חיצוני עושה timeout — והריצה נשארת תקועה באמצע בלי שנרשם למה.

לכן `POST /api/sync` מחזיר **`202` מיד** ועובד ברקע:

```json
{ "started": true, "note": "Running in the background — poll GET /api/runs" }
```

התוצאה מגיעה ל-`GET /api/runs`. שורה עם `finished: false` היא ריצה שלא הגיעה לסופה — תהליך שהופעל מחדש או בקשה שננטשה — וזה **לא** אותו דבר כמו ריצה שנכשלה. `outcome` אומר את זה במפורש.

`?wait=true` שומר על ההתנהגות הישנה למי שיכול להמתין.

### התזמון

השירות החינמי נרדם, אז טיימר פנימי לא אמין. הטיימר קיים כגיבוי, אבל **הטריגר האמיתי הוא קריאה חיצונית**:

```
POST https://your-app.onrender.com/api/sync
Authorization: Bearer <API_TOKEN>
```

תזמן את זה בשירות חינמי כמו cron-job.org כל שעה. הקריאה גם מעירה את השירות וגם מרעננת את קטלוג המקורות — כך שמקור חדש ב-CRM כבר יהיה עם שם כשהליד הראשון דרכו ישנה סטטוס.

כדאי לתזמן לצידה גם את שתי אלה:

```
POST /api/events/enrich     ← מזהה מקור לאירועים שהקריאה נכשלה עליהם
GET  /api/outbox            ← מה לשלוח עכשיו, מורכב ומוכן
```

`/api/events/enrich` בטוח להריץ שוב ושוב: הוא נוגע רק בשורות שעדיין ממתינות.

### משתני סביבה

`render.yaml` מייצר את `API_TOKEN` ו-`WEBHOOK_SECRET` לבד ומחבר את `DATABASE_URL`.

**כל שאר ההגדרות רשומות ב-`render.yaml` במפורש, גם אלה שיש להן ברירת מחדל בקוד.** הסיבה פשוטה: משתנה שיושב רק כברירת מחדל בקוד לא מופיע בדשבורד של Render, ואי אפשר לנהל בנוחות משהו שלא רואים. ככה שינוי של host או של נתיב הוא שדה לערוך, לא deploy.

מה שידני ב-Dashboard (Render מבקש בהקמה, ולא נכתב לקובץ):

```
SURENSE_CLIENT_ID
SURENSE_CLIENT_SECRET      ← אחרי סיבוב
SVIX_WEBHOOK_SECRET        ← ה-whsec_ מ-Svix
REDIRECT_ALL_TO            ← כתובת הפיילוט; ריק = אוויר
```

ומה שגלוי וניתן לעריכה בדשבורד:

| משתנה | ערך |
|---|---|
| `SURENSE_TOKEN_URL` | `https://api.surense.com/oauth/token` |
| `SURENSE_API_BASE` | שני hosts, מופרדים בפסיק; הראשון שעונה מנצח |
| `SOURCE_CATALOG_PATH` | `/customers/sources` |
| `MIRROR_LEADS` | `false` |
| `STATUS_COLUMN` `SOURCE_ID_COLUMN` `ASSIGNEE_COLUMN` `CLIENT_NAME_COLUMN` `LEAD_NUMBER_COLUMN` | שמות השדות ב-CRM |
| `TIMEZONE` `ACTIVE_DAYS` `ACTIVE_HOURS` `MAX_SENDS_PER_RUN` | תזמון ובלם |

### אחרי ששינית משתנה — תבדוק שזה תפס

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" $URL/api/crm
```

{ "settings": { "clientId": "cid_0123…cdef (24 chars)", "clientSecretSet": true,
                "tokenUrl": "https://api.surense.com/oauth/token" },

`scope` הוא מה שהטוקן **באמת** נושא, ולא מה שהוגדר במסך של Surense — הפער בין השניים הוא בדיוק מה שמסתתר מאחורי 403 על endpoint חדש.

**המזהה ממוסך והסוד לא מוחזר בכלל.** דף הגדרות שמחזיר את האישור הוא לא דף הגדרות.

שמות העמודות הם ברירות מחדל שמתאימות ל-CRM הזה (`statusName`, `fullName`, `number`, `sourceId`), ולא צריך להגדיר אותן. `SOURCE_COLUMN` ריק בכוונה: אין עמודת שם מקור, והפתרון עובר דרך `sourceId` וטבלת `sources`. אם Surense תוסיף אי-פעם עמודת שם, הגדרתה כאן תעקוף את הלוקאפ בלי שינוי קוד.

הרשימה המלאה ב-`.env.example`.

## אבטחה

**ה-API לא פתוח לכולם, ובכוונה.** הוא מגיש שמות לקוחות, טלפונים וסטטוסים. endpoint לא מאומת בכתובת ציבורית הוא דליפת מידע. לכן `API_TOKEN` נדרש בכל נתיב חוץ מ-`/health`, וההשוואה היא `timingSafeEqual`.

אם אתה צריך גישה מוגבלת יותר לצד שלישי, זו הרחבה של שכבת האימות — לא ביטול שלה.

**עוד שתי נקודות:**

- ה-`WEBHOOK_SECRET` נפרד מה-`API_TOKEN`, כדי שאפשר יהיה לבטל שולח בלי לנתק את כל הקוראים.
- האישורים שלך ב-Surense נושאים `leads:update` — הרשאת כתיבה שהקוד הזה לא משתמש בה. אם Surense מאפשרת client עם `leads:read` בלבד, כדאי. אז "לא נוגעים ב-CRM" הופך לתכונה של האישור, לא הבטחה של הקוד.

### עמידות: ה-webhook לא מפיל את השירות

`test/robustness.test.js` יורה בדחיפה כל מה שאפשר: גוף ריק, JSON לא תקין, מערך, `null`, מספר, מחרוזת, אירוע לא מוכר, `diff` שהוא לא אובייקט, `leadId` מקונן, ותאריך שאינו תאריך. **הכלל: אף אחד מהם לא מחזיר 500** — כי 500 הוא בדיוק איך שמבקשים מ-Svix לשלוח את אותו גוף שוב, ושוב.

שלושה באגים אמיתיים נמצאו ככה ותוקנו:

1. **דחיפה בלי שדה `date`** הפילה את הבקשה — בדיקת חותמת הזמן של הסנכרון זרקה שגיאה. עכשיו חותמת לא שמישה נופלת ל"עכשיו": טעות של שניות, במקום לאבד את האירוע.
2. **גוף `null`** (JSON תקין, לא אובייקט) נכשל בכתיבה ל-`jsonb NOT NULL`. עכשיו נעטף ונשמר.
3. **בית אפס** בתוך הטקסט — Postgres מקבל אותו ב-JSON ופוסל ב-`jsonb`. עכשיו מנוקה לפני הכתיבה.

ובנוסף: CRM מושבת עולה *העשרה* ולא אירוע; אירוע שאי אפשר לפתור נעצר אחרי 5 ניסיונות ולא חוסם את התור.

> הבדיקות רצות טורית (`--test-concurrency=1`). שני קבצי הבדיקה מנקים את אותן טבלאות, ובמקביל הם מוחקים אחד לשני את הנתונים באמצע הריצה.

### שני באגים שהבדיקות תפסו

לא הייתי מוצא אותם בקריאה:

1. **`RETURNING` לא יכול לפנות ל-`EXCLUDED` או לערך שלפני העדכון** — Postgres מחזיר `errorMissingRTE`. כל כתיבת cursor נכשלה בשקט והמיקום נשאר 0.
2. **דף שמצהיר `hasNextPage: true` אבל מחזיר אפס שורות** נספר כקריאה שלמה. קריאה חלקית הייתה מיושמת כאילו היא כל ה-CRM — וכל ליד שלא נקרא היה מסומן כנעלם. עכשיו סתירה כזו נחשבת לקריאה לא שלמה.
